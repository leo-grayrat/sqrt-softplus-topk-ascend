# Case 15 结构性优化：阈值筛选的准入实验

跟踪 [Issue #48](https://github.com/leo-grayrat/sqrt-softplus-topk-ascend/issues/48)。当前已过 Judge 基线为 `exp/fp32-large-k-c15`，15/15 Pass，case 15 为 1.65 ms。本页及工具属于算法研究，不是新的待提交 kernel。

## 先纠正方向依据

上一轮讨论提出阈值筛选时漏查了历史。[2026-09-14 研究归档](deep-research-topk-directions-2026-09-14.md) 已记录 exact pivot-filter 的真实 Judge 总体退化约 17.5%，并指出 `Compare -> GetCmpMask -> GetValue -> scalar count/branch -> GatherMask` 的串行依赖。该数字为历史记录，不是本轮重测，也不是当前 case 15 的退化幅度。

因此不重做逐 64 元素读回 mask、计数并分支的实现。研究问题改为：能否用整行向量掩码和整体压缩，把候选数量读回限定为每行一次，并让完整路径明显胜过当前多行批处理。旧 kernel 的 profile 结论不能直接代替本轮 large-k 的测量。

## 精确性合同

对一行 1024 个值，固定位置采样 m 个值，取样本第 64 大作为阈值 t。样本是原行子集，因此至少有 64 个原行元素大于等于 t；所有小于 t 的值不可能挤掉这些元素进入前 64。保留全部 `x >= t` 后精确排序可恢复 Top-64。

- 必须使用 >= 保留阈值处重复值，不能任意截断候选。
- 候选超过 256 时回退到已验证完整 Top-K；不足 64 也回退并视作需要调查的异常。
- **压缩暂存区必须容纳全部 1024 个值**，不能先向 256 容量写入、事后才检测溢出。
- NaN 不在本次主机模型排序合同内，标记回退；设备实现须核对当前提交的 NaN contract，不能声称模型验证了 NaN 输出。
- ±inf、重复值、最大值集中、采样位置偏置均纳入验证。
- 回退必须在本次调用内完成，不使用 Judge 结果、测试点身份或固定数据分布决定输出。

## 已完成的主机算法实验

工具：[threshold_selection_model.py](../tools/threshold_selection_model.py)。固定种子 20261004，每个配置 3025 行；与整行排序的前 64 值逐项比较，两个配置均通过，另检查 NaN 回退标记。原始结果：[JSON](threshold-selection-model-2026-10-04.json)。这是 Python 主机模型，不是 CANN CPU twin-debug，也没有设备性能含义。

| 采样大小 / 候选上限 | 正态回退 | 均匀回退 | 离散重复值回退 | 正态平均候选数 |
|---|---|---|---|---|
| 256 / 256 | 488/1000 | 471/1000 | 814/1000 | 256.065 |
| 512 / 256 | 0/1000 | 0/1000 | 138/1000 | 127.870 |

两种配置的 16 组集中最大值输入均回退；全相同、全负无穷等也能回退并给出精确结果。0/1000 不是任意分布下的回退率保证。

淘汰 256 采样方案：其随机分布回退已接近一半，不进入调参。仅保留 512/256 作为有界设备研究候选。该方案还需要处理样本 Top-64，加上最多 256 候选的排序，Sort32 输入槽位预算为 512+256=768，较原始 1024 只少 25%；这不是总计算量或耗时的节省率，还要支付采样、阈值读回、整行比较、压缩、计数、补齐以及可能损失跨行 batching 的成本。

复现：`python tools/threshold_selection_model.py --output notes/threshold-selection-model-2026-10-04.json`。

## 已检查接口与未解决问题

本机 CANN 9.0.0 的 `asc/impl/basic_api/dav_c220/kernel_operator_vec_gather_mask_impl.h` 显示，float + uint32 mask 的 GatherMask 实现通过 `vreducev2` 执行压缩，带计数版本随后调用 `GetRsvdCnt()`。这提供整体压缩接口的依据，但不证明跨 repeat 布局、同步开销或多行可变长度布局已验证。只使用公开接口，不直接包含内部实现头。

下一项设备准入测试必须先验证整行 Compare/GatherMask 的 mask 布局、全选/全不选/交替/跨 repeat 边界以及实际 count；不能臆造 API，也不能将整体调用称为“没有向量到标量同步”。

## 后续执行与停止标准

1. 单独 probe 验证整行掩码与压缩，目标是每行一次候选计数读回；若仍需要逐块标量计数，停止此路线。
2. 仅针对 FP32 E=1024/k=64，实现 512/256 完整路径，包括样本选择、阈值、压缩、候选排序、原路径回退、变换和输出。先测同一组 adversarial 输入与现有生产 probe 的尾 batch/多核情况。
3. 与当前基线用同输入、同核数、同输出比较完整 kernel；至少测 T=4、16、64，并单列回退输入成本。不能只测 GatherMask 或省下的 Sort32。
4. 预先设研究门槛：连续 batch 模型耗时至少改善 20%，回退路径额外成本不超过 10%；不达标则归档停止，不扫阈值、采样数或候选容量参数。门槛是项目决策，不是硬件定律；仿真过门槛仍不证明真机提升。
5. 通过本地正确性、设备编译和完整路径门槛后，才接入独立待测分支让用户运行全部 15 个 Judge 点。真实性能比较以 1.65 ms 为当前基线，能重复测量时确认波动范围。

本页记录实验前计划。后续已完成整行压缩 CANN CPU 检查、完整原型及同输入仿真，详见 [设备原型结果](threshold-device-probe-2026-10-04.md)。正常输入连续 batch 改善仅 8.8% / 11.3%，未达到 20% 门槛，本轮停止。submission 不变，无新的 CANNJudge 待测文件。
